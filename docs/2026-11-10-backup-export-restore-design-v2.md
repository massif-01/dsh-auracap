# AuraCap 备份导出与恢复详细设计方案 V2

日期：2026 年 11 月 10 日。状态：供评审，尚未实施。代码基线：`6598075`。

本版替代 [V1 方案](/Users/massif/dsh-auracap/docs/2026-11-10-backup-export-restore-design.md)，收敛 [方案审查中的十项问题](/Users/massif/dsh-auracap/docs/2026-11-10-backup-export-restore-design-review.md)。本文是完整方案，实施时无需将 V1 与审查意见拼接使用。

目标是把 AuraCap 当前保存的内容导出成文件，需要时完整恢复。恢复替换整个内容库，不合并、不去重，不为恢复重新调用模型。已确认的单列设置布局、导出菜单与恢复弹窗层级保持不变。

图片按用户最新决定处理：**当前可用的图片版本就足够，不要求找回最初上传的字节。已有本地图片直接保存；只剩 Harness 处理过的版本时，保存那个版本。** 因此统一使用“图片”一词，不再用“原图”作无法确认的质量承诺。

## 一 产品范围和恢复结果

| 操作 | 结果 | 用于恢复 |
| --- | --- | --- |
| 导出整个包 | 当前图片、已保存文字、总结、分组、洞察及项目上下文的 `.auracap.zip` | 可以 |
| 仅导出图片 | 可独立查看的图片 ZIP | 不可以 |
| 仅导出文本内容 | 可独立阅读的 Markdown 集合和目录 ZIP | 不可以 |
| 从备份恢复 | 当前内容完整替换成包内内容 | 只接受完整备份 |

完整恢复保留条目 ID、条目顺序、内容时间、总结全文、标签与实体、分组成员和处理状态、合并正文，以及已有日洞察、周迹、月迹、岁迹。已删除且不在当前库中的内容不会因备份重新出现。备份中没有的类别恢复为空，不从当前库补齐。

图片恢复后可直接查看，并有本机有效的宿主附件引用，供以后用户主动重试总结使用。文档恢复已保存的提取文字与总结，不包含原始 PDF，不重新解析 PDF。软件从未保存过的文字不会通过备份补出，文本导出不调用 OCR、翻译或其他模型。

### 当前设备保留的内容

API Key、GitHub 授权与连接配置、Agent 读取权限、内容语言设置及视图偏好保持当前设备的值；空白设备保持未连接、未授权。图片描述符、索引和调度保护状态由本机建立，不迁移旧设备的运行状态。

用量、费用和调用次数不导出。恢复成功后用量清零；失败并回滚时保留原用量。当前设备的导出操作记录不随恢复回退。

### 不纳入本期

不做云同步、自动快照、增量备份、合并恢复、部分恢复、Markdown 反向导入或历史原始图片追溯。不打包宿主整个附件库，不迁移凭据、设备队列状态、缓存或临时文件。

本期只提取备份正确性所需的运行时和任务边界，不顺带重构整个插件，也不增加账号、密码或备份管理页面。

## 三 导出流程与成功语义

点击菜单选项直接开始对应导出，不增加格式确认窗口。

```text
选择类型 → 等待现有处理结束 → 建立一致快照 → 打包 → 文件可下载
                                                       → 交付下载
```

等待阶段可取消。快照完成后释放内容写入限制，再从独立快照打包；用户无需等到下载结束才能继续导入或编辑。准备中显示真实阶段和可获得的数量，不显示虚假百分比。

| 类型 | 默认文件名 |
| --- | --- |
| 完整备份 | `AuraCap-YYYY-MM-DD-HHmmss.auracap.zip` |
| 图片 | `AuraCap-images-YYYY-MM-DD-HHmmss.zip` |
| 文本 | `AuraCap-text-YYYY-MM-DD-HHmmss.zip` |

文件名使用导出设备本地时间。`exportedAt` 是快照形成时间，保存为带时区的标准时间，不使用下载时间代替。

**文件准备好、交付下载、保存到磁盘是不同状态。** ZIP 准备完毕显示“文件已准备好”；完成向下载端传输后可显示“已交付下载”。没有宿主明确的保存完成事件，就不显示“已保存到某目录”。

最近完整备份时间只统计成功交付过的完整备份，以这些备份中最新的 `exportedAt` 显示。失败、仅准备好、图片或文本导出不更新；重新下载旧备份不把旧内容标成今天的新备份。记录包含快照时间、交付时间、文件名与任务 ID，不进入备份包。

## 四 导出内容和严格快照读取

### 内容清单

| 内容 | 完整包 | 图片包 | 文本包 |
| --- | --- | --- | --- |
| 当前图片文件 | 全部图片条目各一份 | 全部图片条目各一份 | 不包含 |
| 片刻、文档已保存文字和总结 | 结构化内容 | 不包含 | Markdown |
| 标签、实体、来源资料 | 保留 | 不包含 | 可读文字 |
| 分组关系、合并正文、手动或忽略状态 | 保留 | 不包含 | 合并正文及成员索引 |
| 已有日洞察、周迹、月迹、岁迹 | 保留 | 不包含 | Markdown |
| 项目上下文 | 保留 | 不包含 | 单独文件 |
| 本机设置、用量、凭据、原始 PDF | 不包含 | 不包含 | 不包含 |

### 快照读取的唯一入口

备份模块使用专用的严格读取函数，不调用会用空值掩盖错误的 `loadItems`、`loadDigest` 等 UI 读取函数，不使用省略文档全文的列表接口，也不以索引缓存代替真实内容。

取得内容独占权后，按以下顺序建立快照：

1. 枚举支持的内容路径，读取完整 JSON，验证结构与记录关系。
2. 检查磁盘内容与已结束处理后的运行时持久化业务字段一致；排除纯缓存和读取时生成的维护字段。有未落盘差异则失败，不能任选一份生成备份。
3. 为每个图片条目选择可用图片，将其字节复制到独立任务目录，读取并记录实际类型。
4. 把内容记录转为可迁移结构，写出快照文件及文件清单，核对数量。
5. 全部复制完成后释放独占权。之后发生的删除或编辑不影响本次快照。

快照读取不得顺带修复条目、更新业务时间、重算分组或改写实体名称。

### 不存在、为空与损坏的区别

| 情况 | 规则 |
| --- | --- |
| 全新库没有 `items.json` | 仅在运行时也无条目，且没有图片、分组成员或洞察等内容痕迹时按空条目处理；可以单独存在项目上下文 |
| `items.json` 存在且为合法空数组 | 正常空库 |
| 缺少分组或项目上下文文件 | 只在运行时对应内容也为空、没有矛盾引用时生成协议规定的空结构 |
| 洞察目录不存在 | 视为没有该类洞察 |
| 已枚举到的 JSON 无法读取、解析失败或结构不符 | 本次完整导出失败，指出内容类别；不忽略文件 |
| 图片本地文件不可用，但宿主仍有可用图 | 按第五节的明确替代来源保存图片，不丢条目 |
| 两种图片来源都不可用 | 完整包和图片包失败；文本包仍按文字本身的完整性判断 |

不同导出类型只严格检查自己的依赖。图片导出依赖条目和图片，不因无关洞察文件损坏而失败；文本导出依赖文字、分组与洞察，不因附件缺失而失败。完整包检查所有纳入范围的内容。

## 五 图片文件与宿主附件分离

### 选择当前可用图片

每个图片条目优先读取其 `imageFile`。文件可读取、可识别且属于支持的图片类型，就原样复制；不要求证明它是否经过宿主处理，也不重新压缩。

本地文件缺失、不可读或无效时，使用该条目的宿主附件描述符调用 `attachments.readImage`。读取成功并验证实际格式后，原样保存返回的图片。它可以是 Harness 的规范图，这是符合用户需求的有效图片来源。

两个来源都失败时，不能静默略过图片，也不能生成空图片占位后声称完整。界面列出无法读取的条目并允许重试；不扩大为自动修复所有历史图片。

### 两套元数据的职责

| 数据 | 用途 |
| --- | --- |
| 图片文件的实际类型、字节数、哈希和相对路径 | 备份校验、恢复落盘、图片文件下载及本地图片响应 |
| 本机 `image` 附件描述符 | 后续用户主动总结时交给模型；由本机 SDK 生成 |

旧宿主 `attachmentId` 不写入可迁移条目。恢复时保存图片文件，再调用本机 `attachments.saveImage` 得到新的描述符。这个保存动作不调用模型，可能生成宿主自己的规范图，但不能因此改写已恢复的图片文件。

恢复时把真实类型写入运行时条目的 `imageFileMediaType`，与 `imageFile` 一起落盘，使重启后也有准确的文件类型；旧条目尚无此字段时从实际图片字节识别。返回 `imageFile` 的 HTTP 响应必须使用该类型，不能使用规范图描述符的 `mediaType`。附件类型、尺寸和字节数也不能反向覆盖图片文件元数据。

完整备份导出前，使用当前宿主的图片接纳校验能力检查所选图片可重新保存；不为检查而调用模型。宿主版本或图片接纳规则不兼容时，恢复在切换前失败并保留原库。不能承诺任意未来宿主都接受历史图片。

恢复图片与包内对应图片哈希一致，表示没有改变备份中的图片字节，不承诺它是最初上传版本。

## 六 完整包协议

### 目录

```text
manifest.json
items.json
groups.json
memory/profile.json
digests/YYYY-MM-DD.json
insights/week/<周期键>.json
insights/month/<周期键>.json
insights/year/<周期键>.json
media/<条目ID>.<实际格式扩展名>
```

`items.json`、`groups.json` 和 `memory/profile.json` 在空备份中也存在，按协议写出合法空结构，manifest 始终存在；没有内容的洞察与图片目录可以不存在。按内容清单生成 ZIP，不直接压缩当前数据目录。

`state.json`、`memory/settings.json`、`memory/usage.json`、实体索引缓存、运行时身份、恢复保护基线、事务记录和任务文件不进入包。

### Manifest

| 字段 | v1 定义 |
| --- | --- |
| `format` | 固定 `auracap-backup` |
| `formatVersion`、`contentSchemaVersion` | 均为 `1`，V2 是方案修订号，不是已发布协议升级 |
| `exportId` | 此次快照的唯一 ID |
| `exportedAt` | 快照时间 |
| `exportTimeZone` | 导出时设备的 IANA 时区，用于解释导出目录和时间，不覆盖恢复设备时区 |
| `sourcePluginVersion`、`sourceHostVersion` | 导出端版本信息，不按版本字符串相等决定兼容 |
| `counts` | 图片与文档条目数、分组数、日周月年洞察各自数量 |
| `media` | 每个图片条目的 ID、文件路径、真实类型、字节数及名称信息 |
| `files` | 除 manifest 自身外，全部内容文件的相对路径、字节数和 SHA-256 |

每个图片条目对应一份图片，不跨条目去重。片刻总数是图片和文档条目总数，合并结果不额外算片刻。恢复确认数量从通过检查的内容计算，再与 manifest 比对。

ZIP 内容路径与文件清单必须完全对应，不能通过遗漏清单把某个业务文件悄悄排除。拒绝重复路径、越界路径、绝对路径、符号链接以及大小写或路径规范化后冲突的文件。

### 内容适配

条目保存 `id`、`kind`、`createdAt`、`updatedAt`、`status`、`text`、`document`、`summary`、`error`、`model`、`contentLanguage`、`memoryVersion`、允许的来源信息和媒体关联。媒体关联使用包内 `imageFile` 路径，真实类型放在 manifest 的 `media` 中；本机 `image` 描述符不写入包，本机 `imageFileMediaType` 由这份真实类型重建。保留数组顺序。旧图片条目缺少 `kind` 时从图片关系判断，文档从已保存文字或文档信息判断，不改变它们的内容。

总结对象、洞察正文和合并结果不重新解析成一套缩减内容。来源只保留内容溯源字段，例如类型、文件名、asset ID 和摘要值；不从设备状态复制任何字段。分组保留成员顺序、主条目、来源、状态、忽略标记、合并结果和业务时间。

现有可迁移字段在适配器中显式列举。发现未支持的持久化业务字段时，完整导出失败并要求更新适配器，不直接忽略而造成数据丢失；总结正文等已定义内容对象中的额外内容字段可以原样保存。

检查分组必须有有效成员、成员不得互相冲突，图片条目必须有图片。洞察中指向已删除内容的历史来源允许保留，不为了修引用删除正文或重新生成。

导入支持本功能生成的 v1 协议，不直接支持手工压缩的旧目录。未来协议迁移使用纯数据转换，更高且无法理解的协议明确拒绝；不调用模型补字段。

## 七 图片和文本的独立导出

### 图片包

```text
images/
  YYYY-MM-DD/HHmmss_<完整条目ID>.<实际格式>
  undated/<完整条目ID>.<实际格式>
```

按第五节选择当前图片，原样保存。ZIP 只放图片，不夹带条目数据库或文本。名称使用完整 ID 避免覆盖，不做内容去重。无图片时提示“当前没有可导出的图片”，不生成空 ZIP。

日期和时间按导出设备的 `exportTimeZone` 从条目创建时间生成；无效历史时间放入 `undated/`，不丢文件。

### 文本包

```text
README.md
片刻/<条目ID>.md
分组合并/<分组ID>.md
日洞察/YYYY-MM-DD.md
周迹/YYYY-Www.md
月迹/YYYY-MM.md
岁迹/YYYY.md
项目上下文.md
```

`README.md` 提供导出时间、分类数量、时间排序的文章目录和范围说明。片刻文件按标题、时间与来源、总结正文、摘录等其余已保存文字、标签与实体、文档已保存原文的顺序组织，不重复字段、不生成空小标题。

失败条目有已保存文字时仍导出文字并标明状态；无文字图片在目录中说明“暂无已保存文字”。分组合并单独导出并链接成员，各成员片刻文件同时保留。已有日、周、月、年洞察与项目上下文直接保存原文。

使用 UTF-8 Markdown，保留原语言，不识图、不翻译、不重新解析 PDF。只生成实际存在的相对链接；文本包不包含图片，不产生虚假的图片路径。已删除的历史来源标明不可用。生成的标题、链接和代码围栏正确转义，正文不因排版被截断。

确实没有任何可读内容时提示“当前没有可导出的文本内容”；只有文档原文而没有总结时仍可导出。不存在的类别不生成空文件。

## 八 时间和日期语义

条目时间戳、洞察日期及周期键保留原值，不把恢复时间写成内容更新时间。遗留运行状态规范化也不改写这些业务时间。

列表、筛选和时间显示继续使用软件当前的本机时区规则；跨时区换机后，同一瞬间可以显示在不同日期。例如 `2026-11-09T23:30:00Z` 在上海是 11 月 10 日，在洛杉矶是 11 月 9 日。

已有洞察按备份保存的日期及周期键查看，不因条目本地显示跨日而重新归档或生成。图片包目录使用导出时区；它是文件整理方式，不反向改写条目的归档规则。本期不新增全产品的“固定捕获时区”机制。

## 九 内容运行时和任务边界

### 一个运行时入口

插件只保留一个当前内容运行时引用，持有条目、分组、实体索引、恢复保护基线及内容库代次。HTTP、定时任务和 Agent 工具通过它取得当前数据，不分别长期捕获不同的条目数组。

`generation` 是整库载入的代次，由进程会话 ID 和单调递增的载入序号组成，独立于普通列表 revision。启动、成功恢复、发生目录回滚并重新载入时产生新代次；普通新增和编辑只更新原有内容版本。它不进入备份。

磁盘上的 `storeId` 标识一次完整目录身份，服务于恢复事务；它与 HTTP 的 `generation` 职责不同。回滚可以回到同一个旧 `storeId`，但发布新的 `generation`，使先前的请求失效。

### 协调器状态

```text
OPEN → DRAINING → SNAPSHOTTING → OPEN         导出
OPEN → DRAINING → RESTORING → OPEN            恢复成功或已回滚
                              → RECOVERY_REQUIRED  无法确认完整库
```

进入 `DRAINING` 后拒绝新内容任务，等待已获准任务的最后一次写入结束。等待可以取消；取消后回到 `OPEN`。不是先等待再暂停入口，避免等待期间不断出现新任务。

同一协调器按操作区分范围：导出只需要内容一致，纯设备授权、连接配置提交不参与内容快照，因此不等待用户完成设备授权；恢复会替换整个目录，额外限制和等待本机配置写入。内容与配置同时变化的任务按内容任务登记，不能借此跳过等待。

### 任务登记范围

| 写入者 | 被登记的最小工作单元 | 暂停行为 |
| --- | --- | --- |
| 本地图片、文档上传和直接图片接收 | 已接纳文件的读取、附件保存、条目保存、总结与最后的索引及分组写入 | 接纳前检查入口；已接纳的单项完整结束 |
| 手机同步 | 一个 asset 的下载、入库、派生总结、队列确认与清理 | 不再领取下一项；当前项的子任务全部结束才退出 |
| 手动重试或分组合并 | 从状态变化到模型结束和最后一次写入 | 新操作拒绝，已有单项结束 |
| 自动或手动洞察 | 一个周期的处理和落盘 | 批次不再启动下一个周期 |
| 实体补全 | 一个条目的提取和全部写入 | 批次停在条目之间，旧批次退出，之后需重新选取待处理条目 |
| 启动图片迁移 | 一个条目的读取与保存 | 下一条暂停；切库后不携带旧条目引用继续循环 |
| 项目上下文、设置、删除、分组修改 | 完整校验及写入 | 已开始的结束，新操作暂缓或返回忙碌 |
| 系统截图监听 | 发现文件后的导入工作单元 | 暂停领取；用户取消恢复后可继续监听，成功切库则关闭旧监听 |
| GitHub 授权、重新连接和凭据续期 | 一次完整的本地授权状态提交 | 恢复前不允许仍有授权状态提交跨越切换 |

请求返回、`syncing=false` 或某个 busy 标记消失都不等于登记任务结束。异步派生总结沿用父任务的登记资格，或在父任务释放前被可靠登记，不能处于无人追踪的间隙。最后的失败处理和 `finally` 写入也属于任务。

批次容器不作为永远等待的父任务：每项完成后检查入口，发现暂停就退出，不在持有父资格时等待下一项资格。未领取的手机文件不删除、不写 processed；未处理的实体条目以后从当前库重新选择。

已开始的设备授权可能等待用户数分钟。首次确认恢复时，在关闭入口前检查是否有尚未结束的授权流程，包括正在申请设备码、pending 和 provisioning。若有则返回忙碌并保留预览，不进入 `DRAINING`、不占执行名额，提示“请先完成或取消正在进行的手机连接”。检查与关闭入口不可交错，不能让新授权插入；不能先冻结入口，再等待需要用户完成的授权。普通已连接设备的同步和续期则等待当前工作单元结束。授权流程状态提交也经过同一登记入口，不能只禁用按钮。

每次实际内容写入验证任务所属的 `generation`，禁止跨代次写入。正常运行中若仍发现泄漏的旧任务，拒绝其落盘并记录错误，不能让它创建一个新的正式目录。

等待不主动取消模型，也不重新发起模型。允许用户取消等待；如果现有任务没有正常结束，就保持等待或让用户取消，不用“超时后强行切库”绕过一致性。

## 十 旧界面和旧请求的失效规则

所有内容读取在开始时绑定运行时与 `generation`，响应携带这一代次，不能在发送前给旧数据贴上最新代次。内容修改请求携带读取时得到的代次。服务端在接纳任务和实际执行前校验，不匹配返回 `409 LIBRARY_CHANGED`，不自动把旧请求重放到新库。

新鲜的独立上传在接纳时绑定当前代次；不把手机 Shortcut 的既有协议改成必须提交前端代次。它仍通过同步领取和任务登记限制，恢复期间保持在远程队列中。

整库发布只调用一个前端重置入口：

1. 停止旧内容轮询，增加请求代次或中止旧请求；拒绝旧异步响应回填。
2. 清空条目、分组、洞察、实体、搜索、关联内容、错误与忙碌状态，关闭原库详情。
3. 重新挂载项目上下文等拥有本地编辑状态的内容组件，丢弃旧草稿及 `savedNote`，不能仅更新父组件 props。
4. 清理原库已读标记，按新库重新加载；保留视图偏好和设备设置。
5. 从新代次读取数据，再恢复轮询。备份任务区域独立于内容组件，继续显示本次恢复结果。

另一窗口即使尚未收到新代次，也无法用旧代次修改当前内容。它收到 `LIBRARY_CHANGED` 后执行同一个重置入口，不逐个接口补刷新。

目录实际切换到发布完成之间暂停内容读取；不把目录暂时缺失解释成空库。备份任务状态接口保持可用。准备阶段失败且未切换目录时，不需要清空仍有效的编辑器。

## 十一 恢复交互和内容状态

### 选择与检查

标题“从备份恢复”，说明“选择由 AuraCap 导出的完整备份包”。主文件过滤为 `.auracap.zip`，实际依据包内协议判断，不能靠改后缀通过检查。

上传和检查只写临时任务目录，不改变当前库、不建宿主附件、不调用模型。支持取消；关闭页面不自动取消服务端任务，重新打开可查询接回，未提交任务重启后需要重新选择。

### 确认

通过检查后显示文件名、快照时间、“条片刻／张图片／篇洞察”三项数量和包含范围。有文档时补充文档数量。

> 当前内容将被完整替换。
>
> 恢复到此备份保存时的状态，不合并当前数据。已有总结与洞察直接恢复，不重新调用模型。
>
> 设备连接与权限设置保留，用量记录清零。

保留“重新选择”和“恢复此备份”。一次确认即开始恢复，不再增加相同的二次确认。空备份明确显示“这是空备份，恢复后当前内容将被清空”。

### 等待、执行和完成

```text
检查通过 → 用户确认 → 等待现有处理 → 准备内容与图片附件 → 切换并提交 → 完成
```

等待阶段可取消。进入准备内容后不提供中途取消，关闭按钮、Esc 和遮罩不关闭执行中的弹窗。使用真实阶段和图片数量进度，不展示事务路径或附件 ID。

成功仅在事务提交确认且新运行时可读后显示“恢复完成”。失败只有在旧库已经确认可用时才能显示“恢复失败，已保留恢复前的内容”。提交成功但载入尚未完成时显示“内容已恢复，正在完成载入”，不能向用户建议再次恢复。

### 保存状态

| 包内状态 | 恢复状态 |
| --- | --- |
| 总结完成、失败及已保存内容 | 原样保留 |
| 遗留生成中 | 转为失败，说明“备份时生成未完成，可手动重试”；不自动重试 |
| 已合并、手动或忽略分组 | 保留决定和合并结果 |
| 已有洞察 | 原样恢复 |
| 不存在的洞察 | 保持不存在 |

运行进程不可迁移。状态规范化在暂存目录完成，不改写业务时间。恢复和恢复后的启动使用只构建索引、不回写条目实体的载入路径；不运行会重新计算已有分组的启动初始化。正常后续新增或删除仍按既有分组规则处理，继续保护手动和忽略状态。

## 十二 恢复不触发模型与后续调度

恢复只做文件处理、结构校验、图片附件保存、运行状态规范化和本地索引构建，不能复用会启动总结的普通导入接口。

等待期间正在完成的模型属于恢复前已接纳任务；恢复本身不启动模型。切换完成后，新收到的手机或本地材料按独立的新导入处理，不把它算作恢复重生成。

### 本机恢复保护基线

在暂存内容完成规范化后，为恢复内容建立固定的语义基线，保存在本机运行文件中，不进入导出包。基线覆盖：

- 条目：ID、种类、创建时间、可供生成的状态及已有总结文字、标签和实体等实际输入字段。
- 分组：成员及顺序、处理状态、合并结果及实际来源信息。
- 已有日周月年洞察：周期键、标题、正文及来源关系。

指纹使用稳定的字段投影，保留有语义的数组顺序；排除 `attachmentId`、本机路径、规范图尺寸、`updatedAt`、重建索引时间和 UI 状态。不得直接哈希整个运行时对象。

### 同一个自动资格判断

日洞察与周期洞察在执行现有自动规则之前，先取得**实际参与该次生成的材料节点**：条目、合并结果及使用到的下级洞察。生成材料和资格判断使用同一组来源选择逻辑，避免判断一套依赖、提示词又用另一套。

若这些节点全部存在于恢复基线且语义指纹相同，不为它们补生成或自动刷新。若有新增节点或语义变化，允许进入原有自动资格判断；这只是解除恢复保护，不改变原有时间间隔、数量阈值或“已有周期结果不自动覆盖”等规则。

| 事件 | 自动行为 |
| --- | --- |
| 只恢复、重启、过午夜或跨周月年 | 基线内容不自动生成 |
| 仅宿主附件、索引或维护时间变化 | 不认为有新材料 |
| 新增条目，或手动重试改变了实际材料 | 相关材料可进入原有自动规则 |
| 手动重新生成日或低级周期洞察 | 变化后的洞察可作为更高周期的新材料，再按原规则判断 |
| 删除恢复内容 | 不单独启动模型；按原删除语义处理引用 |
| 删除新增内容，剩余材料重新全部等于基线 | 恢复保护重新成立 |
| 修改语言或项目上下文 | 本身不触发历史批量生成；以后确有新材料或用户手动生成时使用当前设置 |
| 用户主动点击生成、重新生成或实体补全 | 允许按该操作原规则调用模型 |

项目上下文和语言会影响提示词，但不作为自动“新材料”开关，避免一次设置变更重跑历史内容。基线持久化，重启不失效；没有恢复基线的普通库继续使用现有自动行为。

## 十三 恢复事务和中断处理

### 路径和身份

任务和控制文件放在正式内容目录之外，且待恢复、回滚目录与正式目录位于同一文件系统：

```text
<DSH_HOME>/auracap/                         当前库 C
<DSH_HOME>/.auracap-transfer/
  active-restore.json                      当前唯一未结束事务的指针
  export-history.json                      当前设备的完整备份交付记录
  jobs/<任务ID>/
    incoming.zip
    next/                                  待恢复库 S
    previous/                              旧库 O
    uncommitted/                           回滚时暂移的新库 Q
    transaction.json                       写前意图与提交决定
  receipts/<任务ID>.json                    已结束任务结果
```

`next` 不是当前库的子目录。任务 ID 和目录路径由服务端生成并绑定，不从包内接收。只有 `active-restore.json` 指向的事务可以决定当前库的恢复；历史回执没有改动当前库的权力。

旧库身份记为 A，新库身份记为 B，使用库内 `library.json` 的 `storeId` 区分。旧库尚无身份文件时，在取得独占权并严格核对内容后创建。身份文件不进入备份。本机恢复基线保存在 `memory/restore-baseline.json`，实体索引仍使用 `memory/entities.json`，两者不进入导出包。事务记录还保存新旧库的必要文件清单指纹，用于验证完整性，不能只认一个标记文件。

### 准备与提交顺序

1. 文件检查完成、用户确认，关闭新任务入口并等待已接纳工作单元全部结束。
2. 严格记录旧库 A 的内容和本机配置。准备 S，将备份的全部内容放入，建立本机图片附件与纯索引，写入恢复基线及身份 B。
3. 复制允许保留的当前设备文件：`state.json` 和 `memory/settings.json`；不把任务队列进程、旧用量、旧索引和旧恢复基线带入。宿主凭据仍留在宿主服务中，不复制整个宿主目录。当前设备导出记录在控制目录中独立保存。
4. 校验 S；需要的文件及目录同步落盘。先可靠写入 `transaction.json` 的准备记录，再可靠发布 `active-restore.json`。在指针可恢复之前不移动 C。
5. 写入并可靠落盘 `intent=switching, decision=uncommitted`。意图表示接下来允许尝试切换，**不声称改名已经发生**。
6. 改名 `C → O`，同步源、目标父目录；再改名 `S → C`，同步相应父目录。全过程保持内容读写暂停。
7. 核对 C 确实是完整的 B，预先构建好可发布的内存对象。可靠写入 `decision=committed`；这是唯一提交点。
8. 以一次运行时引用替换发布 B 和新 `generation`。恢复可读后持久化成功回执，清除活动指针并同步控制目录，再开放任务入口和发送成功结果。
9. 清理本事务的旧库和临时文件；已提交后的清理失败只影响清理，不回滚内容。新任务开始前必须已清除上一事务的活动指针。

暂存写入全部显式指定 S，不能复用默认写向当前 `dataDir()` 的 `saveItems`、`saveGroups` 或有回写副作用的索引函数。候选内存对象使用相对媒体路径，不能残留 S 的绝对路径。

任务状态查询以活动事务和运行时是否已开放为准，优先于已落盘的成功回执。即使回执已写好，活动指针未可靠清除或新运行时尚不可读时，也只返回 `COMMITTED` 和“正在完成载入”，不提前返回成功。这样回执写入与指针清除之间的中断不会产生错误的完成提示。

事务记录、活动指针和回执均用临时文件写入、文件同步、改名与父目录同步的顺序发布。阶段只是辅助信息，恢复决策同时检查目录身份和文件清单。

提交前失败可以回滚；**提交点之后不能再以普通失败路径回滚旧库。** 若发布或回执处理异常，保持内容入口关闭，继续完成已提交的载入，或启动时按已提交事务载入 B；不能重新执行同一个备份覆盖后续内容。

### 未提交事务的恢复表

下表适用于 `decision=uncommitted`，不依赖最后一次意图写在改名前还是改名后：

| 真实目录状态 | 行为 |
| --- | --- |
| C=A，O 不存在 | 旧库从未移走或已经回滚；核对 A，确认回滚完成 |
| C 不存在，O=A | 将 O 改名回 C，同步父目录，再核对 A |
| C=B，O=A | 写入回滚意图；将 C 移到 Q，再将 O 恢复到 C；每次改名后同步父目录 |
| C 不存在，O=A，Q=B | 上一次回滚中断；继续将 O 恢复到 C |
| C=A，O 不存在，Q=B | 上一次回滚已完成改名；核对 A 后写回滚完成决定 |
| 身份矛盾、唯一完整副本无法确定，或缺少必要文件 | 进入 `RECOVERY_REQUIRED`，保留所有副本；不创建空库、不启动迁移或定时任务 |

Q 已存在时先检查它确实属于本事务，不能覆盖不明目录。回滚完成后载入 A、发布新代次、可靠写回滚回执，再清除活动指针；最后才清理 B 的未提交文件。若回滚再次中断，同一表仍可继续使用。

`decision=committed` 时，只接受事务对应的完整 C=B，继续载入并补齐回执和清理；不按未提交表退回 A。C 缺失或身份不符时停止内容启动，不因旧回执或旧目录存在而随意选择。没有活动指针的历史回执只供查询和清理各自任务文件。

### 启动和失败结果

启动顺序固定为：检查活动事务 → 确认正式目录完整 → 载入运行时 → 启动迁移、工具和定时任务。任何容错空库读取均不能跑在事务恢复之前。

未切目录的准备失败保留原运行时；目录已经回滚时，统一重载 A 并更新前端代次。不能只回滚磁盘却保留 B 的条目或索引。

回滚副本只服务于这一笔事务，不是用户可管理的自动备份。宿主附件存储不属于该目录事务；失败时不删除无法确认由本任务独占的宿主附件，不影响聊天图片。

## 十四 任务状态机与重复请求

### 状态

```text
导出：WAITING → SNAPSHOTTING → PACKING → DOWNLOAD_READY
恢复：CREATED → RECEIVING → CHECKING → PREVIEW_READY
      PREVIEW_READY → WAITING → PREPARING → SWITCHING → COMMITTED → SUCCEEDED
```

可取消状态转为 `CANCELLED`；未提交的明确失败转为 `FAILED`；目录切换失败先经过 `ROLLING_BACK`，确认旧库后才能转 `FAILED`；不明状态转 `RECOVERY_REQUIRED`。`COMMITTED` 不允许转为普通失败并重做恢复。

同一时刻只给一个上传检查、快照、压缩或恢复操作执行名额。`PREVIEW_READY` 和 `DOWNLOAD_READY` 不占执行名额，准备好的下载文件不会阻止下一次导出。内容独占限制只在第九节规定的阶段持有，不能与任务执行名额混为一谈。

### 确认和取消

确认处理顺序固定：

1. 根据任务 ID 查找是否已有确认结果；已接受过的确认返回同一执行状态或终态，不再执行。
2. 首次确认只接受 `PREVIEW_READY`，先检查有效期、当前内容代次、授权流程与执行名额。忙碌则保留预览，不冻结内容入口。
3. 在不可交错的状态变更中取得输入文件引用、保留执行名额、绑定执行 ID，并将任务转为 `WAITING`。文件引用防止异步检查期间被过期清理。
4. 在回复“已接受”之前可靠记录确认，按任务串行发布状态。重复确认必须等同一接受记录落盘，不能提前返回成功。复核固定输入文件后关闭新内容入口并等待现有工作单元；关闭入口时再次原子检查授权状态和内容代次，若已变化则结束等待并返回明确失败。
5. 取消与进入 `PREPARING` 的转换互斥，只有一个能成功。异步校验和等待返回后都检查任务仍有效，不执行已经取消的任务。

同一任务 ID 无论双击、两窗口提交或请求重试，都只能触发一次恢复。已失败、取消、过期的任务不复活；明确重试需要新的检查任务。服务端不因网络重试自动重新上传或重新确认。

进程重启时，已接受确认但尚未建立活动事务的任务记为中断失败，原库不变；有活动事务的由第十三节决定结果。回执保留 7 天，过期后旧任务 ID 只返回过期，不作为新任务重建。

### 文件寿命

检查通过但未确认的包与准备好的下载文件，闲置 30 分钟后清理。闲置按实际选择、确认或下载活动计算，后台状态轮询不续期。活动中的上传、压缩、恢复和下载持有文件引用，不受闲置清理影响。

取消和重新选择释放未提交文件。任务结果、预览包、下载文件分别管理；删除 ZIP 不删除已经确认的执行结果。活动事务及其回滚目录绝不按普通过期任务清理。清理只处理服务端登记且身份匹配的本任务目录。

## 十五 容量、下载与可恢复性

### 首版共同边界

首版采用同一套导出与导入限制，作为实施验收目标：

| 参数 | 首版上限 |
| --- | --- |
| ZIP 文件大小 | `2 GiB` |
| 包内文件解压后的总字节数 | `2 GiB` |
| 文件条目数 | `50,000` |
| 单个 JSON 或生成的 Markdown 文件 | `64 MiB` |
| 单张图片 | 同时符合现有插件和目标宿主的图片接纳限制 |

ZIP 使用 UTF-8 文件名及 Store/Deflate，导出产物限制在 ZIP32 可表达范围内，不生成加密或分卷包。检查器与写入器支持同一协议；本期不靠生成 ZIP64 绕过首版容量上限。

限制在一个公共配置中定义，不能导出用一组、恢复用另一组。导出在发布下载文件前检查实际压缩后大小、总展开大小、文件数和图片可接纳性，超限明确失败。任何被正常交付的完整备份，在同版本、同受支持宿主能力下都必须可重新导入。软件升级不改变已交付包的协议解释。

这些数值是设计边界，不是已经跑过的性能结果。实施第一阶段必须在真实 Harness 完成接近边界的往返验证；不能通过时先修订并统一降低导出与导入边界，再交付功能，不允许先导出再告知无法恢复。

### 下载和上传

服务端异步读写任务文件，直接以 `Content-Disposition: attachment`、实际 `Content-Length` 和正确类型交付。前端触发宿主对下载 URL 的处理，不把整个 ZIP `response.blob()` 或 Base64 化。上传以 `File` 二进制流发送，服务端边收边落盘，检查实际收到的大小，不使用现有整包读入内存的 `readBody`。

URL 下载、文件选择、取消和二进制流在真实 Harness 的可行性是第一项实施门槛。若宿主不能支持，不能静默退回整包 Blob 并继续宣称支持 2 GiB；应在实现内容事务之前明确可用链路和对应容量。

打包和下载不随图片总量累积内存，但完整条目 JSON 与现有运行时仍会占内存，因此另设单文件上限。压缩使用异步流，不能用同步压缩阻塞宿主主线程。图片附件逐项重建，避免同时解码全库。

不要求首版做断点续传。中断可在文件有效期内重新下载。只有响应正常完整交付，且不是提前断开的连接，才能更新交付记录；HEAD 或仅查询状态不算导出成功，也不声称磁盘保存完成。

### 磁盘空间

恢复准备前按上传包、展开文件、必要的新目录与附件存储增量估算峰值空间；旧库仍保留，不将其占用误算为空闲。解压和写入过程中继续处理真实空间不足，检查不是可用空间保证。

任务目录、宿主附件与正式库若位于不同卷，分别检查涉及的卷。进入提交前完整写出并校验新库，提交不再依赖大规模复制。空间不足时不切换、不删除旧库来腾空间。

## 十六 接口与模块边界

### 接口

路径都在现有 `/auracap` 前缀下，沿用可信请求边界。耗时处理由任务状态表达，不通过长时间挂起一条确认请求实现。

| 方法与路径 | 作用 |
| --- | --- |
| `POST /api/backup/tasks` | 创建导出任务，或创建等待上传的恢复任务，返回任务 ID |
| `PUT /api/backup/tasks/:id/archive` | 为恢复任务流式上传一个完整备份，结束后进入检查 |
| `GET /api/backup/tasks/:id` | 查询阶段、真实进度、预览、结果或过期状态 |
| `POST /api/backup/tasks/:id/restore` | 确认一次已检查备份；重复请求返回同一执行结果 |
| `POST /api/backup/tasks/:id/cancel` | 取消允许取消的阶段 |
| `GET /api/backup/tasks/:id/file` | 下载准备好的导出文件；HEAD 只查询文件信息 |
| `GET /api/backup/status` | 当前活动任务、当前内容代次和最近完整备份导出记录 |

创建导出任务携带 `type=export, kind=package/images/text`；创建恢复任务携带 `type=restore`。任务创建也接受一次操作 ID，重复的创建请求返回原任务，不重复占名额；未成功创建的操作不触发处理。恢复确认绑定任务 ID、检查过的 ZIP 摘要和确认时的内容代次。

上传文件检查完成后固定为只读任务输入；不能通过第二次上传替换已确认或已检查任务的文件。重新选择创建新任务。前端不提交任意本机读写路径。

统一错误类别包括 `BUSY`、`LIBRARY_CHANGED`、`INVALID_BACKUP`、`UNSUPPORTED_VERSION`、`SOURCE_UNREADABLE`、`IMAGE_UNAVAILABLE`、`LIMIT_EXCEEDED`、`NO_SPACE`、`TASK_EXPIRED` 和 `RECOVERY_REQUIRED`。前端按错误类别显示动作，不匹配底层异常字符串。

### 模块

| 文件或模块 | 责任 |
| --- | --- |
| `client.js` | 已确认界面、任务交互、流式文件上传、URL 下载及内容代次重置 |
| `index.js` | 路由、宿主能力衔接、唯一内容运行时、现有处理入口和启动顺序 |
| `backup/format.js` | 内容协议、严格读取、媒体选择、Markdown 适配、校验和共同限制 |
| `backup/tasks.js` | 任务状态、去重确认、文件寿命与下载记录 |
| `backup/restore.js` | 新库准备、写前事务、提交、回滚和启动恢复 |
| 专项测试与样本 | 协议往返、故障注入、代次失效、任务边界及宿主集成 |

压缩使用成熟 ZIP 库，不另造压缩格式或依赖 shell 解压。具体库版本在第一阶段结合宿主 Node 能力选定并锁定，必须满足第十五节的同一读写协议；不在本设计中假定尚未核验的库 API。

## 十七 空状态和失败文案

| 情况 | 用户看到的结果 |
| --- | --- |
| 等待原有处理 | 正在等待当前处理完成…；可以取消等待 |
| 正在连接手机 | 请先完成或取消正在进行的手机连接，再恢复备份 |
| 无图片或无文本 | 当前没有可导出的图片／文本内容 |
| 本地图片不可用，宿主版本可用 | 使用现有可用图片继续，不冒充最初原图，不丢条目 |
| 两种图片都不可读 | 有 X 张图片无法读取，未生成完整备份；列出条目，允许重试 |
| 内容源 JSON 损坏 | 某类内容无法读取，未生成完整备份；不显示空库成功 |
| 图片包、文本包或普通 ZIP | 这不是完整备份，请选择 AuraCap 导出的 .auracap.zip 文件 |
| 包损坏或文件缺失 | 备份文件不完整，请重新选择或重新导出 |
| 版本不支持 | 此备份需要更新版本的 AuraCap，请更新后重试 |
| 内容代次改变 | 内容库已更新，请重新查看后操作；不重放旧修改 |
| 超过共同容量 | 内容超过当前备份容量上限，未生成文件；说明触及的上限 |
| 空间不足 | 空间不足，无法准备恢复内容。释放空间后重试 |
| 未切换即失败 | 恢复未完成，当前内容未改变 |
| 回滚完成 | 恢复失败，已保留恢复前的内容 |
| 已提交，尚未载入完成 | 内容已恢复，正在完成载入；不提供再次执行同一恢复的按钮 |
| 无法判定完整库 | 恢复需要处理，已暂停内容读写；保留副本，提供错误编号和明确的重启／诊断入口 |
| 清理失败 | 已恢复的结果保持成功，内部登记下次清理，不误报恢复失败 |

错误不自动略过内容、局部恢复或重调模型。除明确的提交成功或回滚完成外，不能用普通成功／失败文案掩盖中间状态。

## 十八 实施顺序与发布验收

### 实施顺序

1. 验证真实 Harness 的 URL 下载、二进制上传、图片校验与附件保存，选定 ZIP 实现，跑通共同容量边界。
2. 固定 v1 内容结构与样本，实现纯内容读取和图片选择，确认严格校验不会漏掉现有文字。
3. 建立唯一运行时、内容代次和完整任务登记；先验证普通导入、生成和分组行为保持一致。
4. 实现三种导出及状态机，再实现恢复准备、事务切换、回滚和启动恢复。
5. 接入恢复保护基线与统一自动资格判断，完成无模型恢复及正常后续处理验证。
6. 接入已确认 UI，落实灰色层级、键盘行为、真实状态和前端统一重置。
7. 更新发布清单，用实际安装包完成隔离宿主验收。

### 验收矩阵

| 范围 | 必须验证的情况 |
| --- | --- |
| 完整往返 | 导出后修改库，再恢复；不混入后来内容；重复恢复不叠加；空包明确清空 |
| 图片 | 本地文件、仅宿主规范图、本地失效后宿主可读、两者均失效；实际 MIME 正确，恢复字节与包一致 |
| 文档和文本 | PDF 原件不入包，提取文字与已有总结保留；无总结但有文字、中文、英文及代码围栏 |
| 分组与洞察 | 手动、忽略、已合并与自动组，日周月年结果、缺失结果、已删除的历史来源 |
| 严格快照 | 损坏和不可读 JSON、列表投影缺全文、缺失图片；不能生成自洽但漏内容的完整包 |
| 后台边界 | 响应已返回但总结未结束、同步剩余批次、迁移读取中、截图监听、授权及凭据续期 |
| 代次 | 打开的项目编辑器、旧请求延迟返回、两个窗口、旧 ID 删除请求、回滚后的重载 |
| 自动处理 | 恢复和重启零调用；跨期、仅维护变化、手动更新下级洞察、增删新材料和设置变化 |
| 状态机 | 重复创建、重复确认、确认响应丢失、取消竞争、终态过期、下载可用后立即再导出 |
| 事务 | 每次写记录、同步、改名及发布前后中断；回滚中再次中断；不明状态不启动空库 |
| 提交点 | 提交前失败回滚；提交后异常只完成新库载入；旧回执不能回退后来恢复的库 |
| 容量与空间 | 共同上限附近的完整导出后导入、超限、中文文件名、空间不足、下载中断、内存不随 ZIP 整包增长 |
| 设置边界 | 不打包凭据和用量；保留当前设备连接及权限；仅成功后用量清零 |
| 跨时区 | 跨日、跨周、跨年的条目与既有周期结果，不改写日期、不补生成 |
| UI | 原布局、灰色小标题、长文件名、焦点、Esc、重复点击、390px 窄窗和减少动效 |
| 安装产物 | 打包清单含新增模块与依赖，隔离安装后从产物完成导出、检查与恢复 |

模型使用记录调用的测试替身，恢复路径出现新模型请求即失败；不为测试消耗真实模型额度。宿主下载、附件保存及实际安装必须在真实 Harness 中另验，静态 HTML 和浏览器模拟不能替代。

### 发布清单

`package.json` 的 `files` 显式加入 `backup/*.js` 及实际需要的资源；更新依赖和锁文件，核对压缩依赖运行环境与许可。不能依靠仓库中的未打包文件运行。

先检查实际打包文件列表，再安装到隔离的宿主数据目录。运行时不能从开发目录回退读取模块。验证交付包括三种导出样本、可恢复的完整备份、故障恢复结果及验收记录。
